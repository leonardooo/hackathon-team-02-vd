# ADR-002: Migracao incremental de dados Adabas para PostgreSQL com dual-write temporario

**Status**: accepted
**Date**: 2026-05-20
**Deciders**: Fabio Guerra (Enterprise Architect + Software Architect), Thaise Dantas (DBA)
**Context tags**: data-migration, database, risk

## Context

O SIFAP legado armazena dados em 4 arquivos Adabas (FDT):
- **BENEFICIARIO** (FNR 150): ~4.2M registros, 30+ campos, hotspot de leitura (11 de 15 programas acessam)
- **PROGRAMA-SOCIAL** (FNR 151): ~45 registros, dados de referencia
- **PAGAMENTO** (FNR 152): ~180M registros historicos, crescimento mensal de ~4.2M
- **AUDITORIA** (FNR 153): ~25M registros, append-only

O Adabas usa um modelo hierarquico (campos MU/PE — multiple-value e periodic groups) que nao mapeia diretamente para o modelo relacional. Exemplos:
- Dependentes sao PE groups dentro de BENEFICIARIO (ate 15 por beneficiario)
- Historico de enderecos sao MU fields

O volume total e significativo (~210M registros) e o sistema nao pode ficar indisponivel durante a migracao — pagamentos de beneficios federais nao podem atrasar.

Restricoes:
- PostgreSQL 16 como target (stack aprovada)
- Zero downtime para pagamentos — beneficiarios dependem financeiramente do sistema
- Dados financeiros historicos devem ser preservados integralmente para auditoria TCU/CGU
- Arredondamento divergente entre programas legados (round vs truncate) — dados historicos refletem essas inconsistencias

## Decision

Adotamos **migracao incremental por bounded context** com fase de **dual-write temporario** durante a transicao.

A migracao segue a ordem de prioridade definida no scope-decisions.md:
1. Programa Social (referencia, ~45 registros) — migracao direta
2. Beneficiario + Dependentes (desnormalizar PE groups em tabelas separadas)
3. Pagamento (bulk load dos historicos, dual-write para novos)
4. Auditoria (append-only, migracao em background)

Cada fase:
1. Cria o schema PostgreSQL para o bounded context
2. Migra dados historicos via `pg_bulkload` ou `COPY` em batches de 100k
3. Ativa dual-write no legado (Natural grava em Adabas + envia para fila que alimenta PostgreSQL)
4. Valida integridade (contagem, checksums, sampling)
5. Corta o legado (Strangler Fig) quando o modulo moderno assume

## Alternatives considered

- **Option A: Big-bang migration (dump completo e cutover em janela de manutencao)**. Pros: simples, um unico corte. Cons: janela de 48-72h para 210M registros, risco de rollback impossivel apos corte, beneficiarios sem pagamento durante a migracao. **Rejeitada** — risco inaceitavel para sistema de pagamentos federais.

- **Option B: CDC (Change Data Capture) com Debezium**. Pros: captura automatica de mudancas, near real-time. Cons: Adabas nao tem conector Debezium nativo, precisaria de custom connector ou proxy, complexidade operacional alta para equipe de 5. **Rejeitada** — nao ha conector Adabas disponivel.

- **Option C (chosen): Migracao incremental + dual-write temporario**. Pros: zero downtime, validacao por etapa, rollback por bounded context, viavel com equipe pequena. Cons: dual-write temporario adiciona complexidade ao legado (Natural deve gravar em fila), periodo de transicao com dois bancos ativos.

## Consequences

### Positive
- Zero downtime — pagamentos nunca param
- Cada bounded context e migrado e validado independentemente
- Rollback granular — se um modulo falha, volta so ele para Adabas
- Dados historicos preservados integralmente para TCU/CGU

### Negative
- Dual-write temporario adiciona complexidade ao codigo Natural legado — mitigacao: camada fina que apenas enfileira JSON para consumer PostgreSQL
- Periodo de transicao com dois bancos ativos aumenta custo operacional — mitigacao: transicao curta por modulo (dias, nao meses)
- PE groups do Adabas precisam ser desnormalizados manualmente — mitigacao: scripts de ETL com validacao automatica

### Neutral
- Dados historicos com arredondamento inconsistente (round vs truncate) sao preservados como estao — novos dados usam a politica unificada (ADR futuro sobre arredondamento)
