# ADR-001: Adotar Modular Monolith com Strangler Fig para modernizacao do SIFAP

**Status**: accepted
**Date**: 2026-05-20
**Deciders**: Fabio Guerra (Enterprise Architect + Software Architect), Leonardo Assis (Technical Lead)
**Context tags**: architecture, migration-strategy, cost

## Context

O SIFAP legado e um monolito Natural/Adabas em producao desde 1997 com 15 programas, 4 DDMs e ~4.2M beneficiarios ativos. O sistema processa pagamentos de beneficios federais (MDAS/SENARC) em ciclos mensais batch.

A equipe de 5 pessoas tem um unico dia de workshop para definir e iniciar a modernizacao. A complexidade do dominio (calculos financeiros compostos, conciliacao bancaria CNAB 240, auditoria) exige separacao de responsabilidades, mas a equipe reduzida e o prazo curto nao comportam a complexidade operacional de microservicos (service mesh, distributed transactions, eventual consistency para dados financeiros).

O legado nao possui CALLNAT entre programas — todos usam sub-rotinas internas via PERFORM. O fluxo e estritamente linear: Cadastro → Calculo → Pagamento → Conciliacao → Relatorios. Isso facilita a decomposicao em modulos dentro de um unico deployable.

Restricoes:
- Stack aprovada: Java 21 + Spring Boot 3.3 + PostgreSQL 16
- Equipe: 5 pessoas, 1 dia
- Dados financeiros exigem consistencia forte (ACID)
- Integracao com SIAFI (STN) via FTP — sem API disponivel

## Decision

Adotamos o padrao **Modular Monolith** (monolito modular) com estrategia de migracao **Strangler Fig**.

O backend sera um unico artefato deployavel (Spring Boot JAR) com modulos internos separados por bounded context (package-by-feature), cada um com suas camadas domain/application/infrastructure. Os modulos comunicam-se via interfaces Java internas (sem HTTP/mensageria entre eles). O banco PostgreSQL usa schemas separados por modulo.

A migracao segue o padrao Strangler Fig: funcionalidades sao migradas incrementalmente do legado para o moderno, com ambos os sistemas coexistindo durante a transicao. Anti-corruption layers isolam o codigo moderno das interfaces legadas (CNAB 240, FTP SIAFI).

## Alternatives considered

- **Option A: Microservicos desde o inicio**. Pros: independencia de deploy, escalabilidade granular, isolamento de falhas. Cons: complexidade operacional (service mesh, observabilidade distribuida, sagas para transacoes financeiras), equipe de 5 nao suporta overhead de DevOps, consistencia eventual inaceitavel para dados financeiros criticos. **Rejeitada** — over-engineering para o contexto.

- **Option B: Monolito classico (camadas horizontais)**. Pros: simplicidade, deploy unico, familiar. Cons: acoplamento alto entre dominios, dificil evoluir independentemente, repete os problemas do legado (God Batch BATCHPGT). **Rejeitada** — nao permite decomposicao futura.

- **Option C (chosen): Modular Monolith + Strangler Fig**. Pros: deploy simples (1 JAR), transacoes ACID locais, modulos desacoplados por bounded context, pode evoluir para microservicos no futuro se necessario, equipe pequena consegue gerenciar. Cons: todos os modulos compartilham o mesmo runtime (se um falha, todos caem), escalabilidade e uniforme (nao pode escalar so o modulo de calculo).

## Consequences

### Positive
- Deploy e operacao simples — 1 artefato, 1 banco, 1 pipeline CI/CD
- Transacoes ACID entre modulos sem complexidade de sagas
- Bounded contexts preparam para futura extracao de microservicos (se necessario)
- Equipe de 5 consegue entregar no prazo do workshop

### Negative
- Falha em um modulo derruba o sistema inteiro — mitigacao: health checks granulares por modulo, circuit breakers internos
- Escalabilidade horizontal e uniforme — mitigacao: para 4.2M beneficiarios o volume e gerenciavel com uma unica instancia otimizada + read replicas

### Neutral
- O padrao Strangler Fig permite que o legado continue rodando em paralelo durante a migracao, reduzindo o risco de big-bang
