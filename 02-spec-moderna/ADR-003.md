# ADR-003: Autenticacao via OAuth2/OIDC com Gov.br substituindo autenticacao Natural nativa

**Status**: accepted
**Date**: 2026-05-20
**Deciders**: Fabio Guerra (Enterprise Architect + Software Architect), Izabella Campos (DevOps Engineer)
**Context tags**: security, authentication, identity

## Context

O SIFAP legado utiliza autenticacao nativa do Natural Security em mainframe IBM zSeries. Operadores acessam via terminal 3270 com usuario/senha gerenciados internamente. Nao ha SSO, MFA, nem integracao com provedor de identidade externo. O controle de acesso e baseado em perfis Natural (OPERADOR, AUDITOR, GESTOR) hardcoded nos programas.

A modernizacao precisa de:
- Autenticacao para operadores MDAS/SENARC (interface web Next.js)
- Autenticacao para auditores TCU/CGU (consulta e relatorios)
- Autenticacao para integracao sistema-a-sistema (API REST)
- Conformidade com e-Gov (Decreto 8.936/2016 — autenticacao digital de servicos publicos)

O Gov.br e a plataforma unica de autenticacao do governo federal brasileiro, implementando OpenID Connect (OIDC). Sistemas federais sao obrigados a utiliza-lo conforme normativa da SGD/ME.

Restricoes:
- Stack aprovada: Spring Security (backend), Next.js (frontend)
- Conformidade com OWASP Top 10 (copilot-instructions.md)
- Secrets via Azure Key Vault apenas — nunca em codigo
- CORS configurado explicitamente — sem wildcard em producao

## Decision

Adotamos **OAuth2/OIDC com Gov.br como Identity Provider** para autenticacao de usuarios humanos, e **JWT (client_credentials)** para autenticacao sistema-a-sistema.

- **Backend**: Spring Security OAuth2 Resource Server valida JWT tokens
- **Frontend**: Next.js usa server-side auth flow (authorization_code + PKCE) — tokens nunca expostos ao browser
- **Perfis**: mapeados de claims do Gov.br para roles Spring Security (ROLE_OPERADOR, ROLE_AUDITOR, ROLE_GESTOR, ROLE_ADMIN)
- **API M2M**: client_credentials grant com scopes restritos, credentials em Azure Key Vault

## Alternatives considered

- **Option A: Autenticacao propria (username/senha em PostgreSQL)**. Pros: independencia de provedor externo, controle total. Cons: viola normativa de autenticacao unica do governo federal, reinventa o wheel (hash, MFA, reset de senha, etc.), responsabilidade de seguranca recai no time. **Rejeitada** — nao-conformidade regulatoria e risco de seguranca.

- **Option B: Keycloak self-hosted como IdP intermediario**. Pros: flexibilidade, suporte a multiplos provedores, federation com Gov.br. Cons: mais um componente para operar (JVM pesada, banco proprio, updates de seguranca), equipe de 5 nao suporta overhead, adiciona latencia na cadeia de autenticacao. **Rejeitada** — complexidade operacional injustificada quando Gov.br ja oferece OIDC direto.

- **Option C (chosen): Gov.br direto via OAuth2/OIDC + JWT**. Pros: conformidade regulatoria automatica, SSO para todos os sistemas federais, MFA nativo, nao precisa gerenciar credenciais de usuario, Spring Security tem suporte nativo. Cons: dependencia de disponibilidade do Gov.br (SLA 99.5%), limitacao de claims customizadas.

## Consequences

### Positive
- Conformidade automatica com e-Gov e normas da SGD/ME
- SSO — operadores usam a mesma credencial de outros sistemas federais
- MFA nativo do Gov.br sem implementacao propria
- Zero gerenciamento de senhas pelo SIFAP 2.0
- Spring Security OAuth2 Resource Server e maduro e bem documentado

### Negative
- Dependencia de disponibilidade do Gov.br — mitigacao: cache de tokens com TTL curto (5min), graceful degradation que permite operacoes read-only com token em cache
- Claims do Gov.br podem nao conter perfil SIFAP diretamente — mitigacao: mapeamento de CPF para perfis em tabela local, sincronizada por admin

### Neutral
- Migracao de usuarios do Natural Security para Gov.br requer vinculacao manual CPF → perfil SIFAP na primeira vez (one-time setup)
